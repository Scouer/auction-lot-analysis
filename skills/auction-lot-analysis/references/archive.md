# Фаза 6: архив, индекс, staging, калибровка

Разбор, оставшийся текстом в чате, потерян. Архив обязателен при любом исходе — но «обязателен» означает «по лестнице», а не «в vault или никак».

## Канон (режим M)

Vault `Vasily_Brain` (путь динамически; записи через Desktop Commander, не через Drive API; в начале сессии читать `Vasily_Brain/CLAUDE.md`).

```
Projects/antique/
  lots/ГГГГ-ММ-ДД-ДОМ-NNN/     # досье лота (code/new-lot.py или вручную)
    source/listing.md           # описание дома дословно
    source/listing.pdf          # страница лота — аукционы удаляют лоты
    source/house-photos/        # все изображения листинга
    research/analysis.md        # полный отчёт по форме
    research/comparables.csv
    marks/  photos/  docs/      # кропы Фазы 0 — в досье
  _index.csv                    # реестр всех лотов (схема ниже)
  authors/                      # база авторов (author-base.md)
  collectors/<имя-slug>.md      # досье заявленного коллекционера (см. ниже)
  sales/ГГГГ-ММ-ДД-ДОМ-REF/     # скан консигнации — один раз на сейл (см. ниже)
  sellers/<дом-slug>.md         # досье продавца
  qa/                           # тестовые и служебные прогоны — вне боевой выборки
```

**Папка сейла `sales/ГГГГ-ММ-ДД-ДОМ-<catalogRef>/`** — выход Ш4 (`consignment.md`). Скан делается
**один раз на сейл** и переиспользуется всеми лотами этого сейла; перед сканом обязательно
проверить, нет ли уже готовой папки.

```
sales/2026-08-21-EDEN-X3YG6FJQR5/
  scan.md              # заключение скана: границы конструкции, тесты, экономика, выводы
  catalog.json         # выгрузка каталога (лоты, описания, цены) — источник, не переписывать
  stats.md             # экономика партии → строка в base-rates.md
  seriality.csv        # тест серийности признака: лот · признак · чтение · уверенность · верификация
  README.md            # где лежат тяжёлые данные (изображения, кропы) вне vault
```

Тяжёлое (галереи, оригиналы, кропы, контакт-листы) в vault **не кладётся** — оно живёт локально
вне vault, а в `README.md` папки сейла пишется путь и состав. Правило общее по vault: он синкается
в Drive, гигабайты изображений туда не идут.

**Досье коллекционера `collectors/<имя-slug>.md`** — заводится всегда, когда дом называет имя
владельца/собирателя. Структура: кто это по внешним источникам (даты, род занятий, семья,
**второе имя 字 и псевдонимы**, супруг(а) — они всплывают в посвящениях) · документировано ли
собирательство и чем · корпус работ, связанных с именем, по внешним базам (с контрольным
запросом) · личный архив: есть фонд или нет, где · что реально выходит на рынок под этим именем ·
**таблица ротации: в каких сейлах и каких домов имя использовано как провенанс** · омонимы
и однофамильцы, с которыми путают · связанные лоты `[[wikilinks]]`.

Досье коллекционера — такой же накопительный актив, как досье автора: одно имя обслуживает все
лоты всех сейлов, где оно заявлено, и делает каждый следующий разбор дешевле.

**Схема `_index.csv`** (колонки = ключам YAML-хвоста; у Запроса/Отказа ценовые поля пустые — легально):

```
lot_id,date,house,url,category,route,outcome,tier,truncated,env,n_photos,
coverage,verdict_auth,fair_low,fair_high,forecast_low,forecast_high,currency,
bid_ceiling,regret,deadline_utc,author_id,dossier_tier,sync_debt,skill_version,
hammer_actual,notes
```

**Досье продавца `sellers/<дом>.md`:** гарантии и их отказы; расхождения витрина/условия; практика каталогизации (концентрация громких имён, «unpublished»-коллекции); ответы на запросы (уклончивость, молчание — с датами); наблюдения о листингах (систематически не снимаемые зоны); публичные обвинения с E-ссылками; прайор канала. Обновляется при каждом лоте дома.

**Тестовые/QA-прогоны** — только в `qa/`, в боевой `_index.csv` не пишутся: калибровочная выборка не загрязняется.

## Staging-лестница (режим C, vault недоступен)

Сверху вниз, первое доступное; в шапке и хвосте — `SYNC-DEBT: да`:

1. **Notion-журнал** — строка лота + полный отчёт страницей; досье авторов → «Authors inbox».
2. **Project docs** (`claude/lots-staged.md`, `claude/authors-staged.md`) — накопительные staging-файлы.
3. **YAML-хвост в чате** — минимум, который есть всегда: хвост самодостаточен для восстановления строки индекса.

Правило гашения долга: ближайшая M-сессия первым делом проверяет staging (Notion inbox, Project docs) и вливает в vault; долг держится видимым, пока не погашен. Молча пропускать архив запрещено; «vault недоступен» = staging, не пропуск.

Разделение ролей хранилищ: **vault — архив** (полные досье, кропы, индекс, база авторов); **Notion — журнал** (человекочитаемая строка на лот: прогноз/факт, статус). Два места — две роли; канон один — vault.

## Что фиксируется всегда

- Все лоты, включая исходы «Запрос» и «Отказ» — отказ с причиной есть обучающая выборка.
- Наблюдения о листинге → досье продавца.
- Досье автора: исход лота в «Журнал обновлений», новые факты дельтой (author-base.md).
- Пришли новые данные по разобранному лоту — **сначала обновить досье, потом отвечать.**

## Калибровка

После сейла в досье пишется фактический молоток (`hammer_actual`). **Основная метрика — прогноз молотка (вилка из §3 формы) против факта**; потолок покупателя — не метрика (он консервативно смещён по построению). Подлинность — вторичная метрика, по факту осмотра вживую/тестов (TL, XRF — после покупки, для калибровки).

**Калибровщик** — регулярная задача, не роль: (M) напоминание/скрипт; (C) еженедельный scheduled task «добрать молотки по открытым lot_id». Раз в 15–20 лотов — сверка: смещение вилки; какая роль ошибается систематически; оправдывает ли себя Fable 5; актуальность fake-списка и полос base-rates; средний размер отчёта (не разбухает ли форма).

`skill_version` в каждом хвосте: дрейф навыка отделим от дрейфа исполнителя.
